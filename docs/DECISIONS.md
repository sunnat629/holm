# Decisions and accepted risks

One line per decision: what we chose, why, the risk we accept, and when to revisit.
The binding design is `docs/superpowers/specs/2026-10-17-holm-v1-design.md`; this file
records the choices made while building Phase 0-1 and planning Phase 2
(`docs/superpowers/plans/2026-10-18-phase-2-holm-core.md`).

- **Local CI replaces GitHub Actions until the repo is public.** Why: Actions is manual-only for now, and `scripts/ci-local.sh` already runs all 8 gates. Risk: a Linux- or Windows-only bug ships unnoticed. Revisit: before going public, re-enable Actions (3-OS CI, scheduled fuzzing, oracle and fuzz jobs, checksummed cargo-deny install) and GitHub private vulnerability reporting.
- **The test-only oracle uses unsafe FFI to libsodium.** Why: an independent Argon2id cross-check for the `argon2` crate, which has no outside audit. It sits in one `#[allow(unsafe_code)] mod ffi` with a `// SAFETY:` comment on every block, in a separate workspace that never ships. Risk: a bug in the test harness itself. Revisit: if the oracle ever joins the product graph (it must not).
- **The oracle ignores RUSTSEC-2026-0367, -0368 and -0369 (zip 8.6.0) in `cargo audit`.** Why: zip is a build dependency of `libsodium-sys-stable`, used by its build script only for Windows MSVC targets, on an archive checked first (the local gate skips the oracle on Windows), in a workspace that never ships. Risk: a build-time issue on a Windows dev machine. Revisit: remove the ignores once `libsodium-sys-stable` moves to zip 9.
- **Nothing is locked in RAM yet (no `mlock`).** Why: locking is platform work, and secrets are wiped on drop. Risk: the OS may swap secrets, including the Argon2 work area, to disk while in use (listed in `docs/CRYPTO.md` known gaps). Revisit: in the platform phase.
- **Timing difference between wrong password and damaged body is accepted, not hidden.** Why: Argon2 dominates the cost, and the difference only shows whether the key unwrap succeeded, which anyone holding the file can test offline at the same Argon2 cost. Risk: none beyond what the file already allows. Revisit: only if an online oracle ever appears. See `docs/CRYPTO.md`, Timing.
- **Nonce misuse resistance by type.** Why: `Nonce` has no `Clone`, `Copy` or `Default`, is made only by `Nonce::random()`, and `seal` takes it by value, so a nonce cannot be reused through the API. Risk: a small API rework later. Revisit: if a format needs deterministic nonces.
- **`rekey` takes `&mut VaultKeys` and replaces the keys only on success.** Why: a failed rekey leaves the old keys working (atomic from the caller's view). Risk: none known. Revisit: if keys become shared across threads.
- **Padding is canonical.** Why: each body has exactly one padded form (16 KiB blocks, u32 LE prefix), and `unpad` rejects any other, so there is no malleable padding. Risk: a future writer must follow the same rule. Revisit: on a format version bump.
- **Full-open fuzzing is deferred to Phase 2.** Why: it needs the Phase 2 body decoder. The header parser and body decoding are fuzzed now. Risk: bugs in the full open path are found by tests, not fuzzing, until then. Revisit: Phase 2.
- **SBOM and the `--all-features` release guard are deferred to Phase 6.** Why: both are release work, and `test-vectors` only exposes the raw Argon2 KAT helper. Risk: none for unreleased code. Revisit: Phase 6.
- **3 `cargo vet` exemptions remain, all dev-only or unused-target.** Why: Phase 2 Task 1 (#13) moved libc and syn 2 and 3 to `cargo vet trust` (syn: dtolnay; libc: its crates.io trusted publisher `github:rust-lang/libc`, because releases since 0.2.190 no longer come from rust-lang-owner), and the dev-only rustix and linux-raw-sys (sunfishcode), windows-sys (kennykerr) and toml_edit, toml_parser and winnow (epage) to safe-to-run trust of publishers that isrg, mozilla and ariel-os already trust; r-efi (unused UEFI target), borsh-derive and proptest (dev-only, no trusted publisher) stay exempt with their reasons in `supply-chain/config.toml`. Risk: a trusted publisher's account, or libc's release workflow, is compromised. Revisit: before the trust entries end on 2027-10-17, and at Phase 6.
- **The cargo-deny-action is pinned to a full commit SHA (v2.1.1).** Why: a moving tag is a supply-chain hole. Risk: the action downloads its binary without a checksum. Revisit: when Actions is re-enabled, move to a checksummed install and keep it on the same cargo-deny version as `scripts/ci-local.sh`.
- **Re-enable Actions and private vulnerability reporting before going public.** Why: SECURITY.md tells reporters to use GitHub private reporting, and the spec wants 3-OS CI. Risk: if forgotten, reports have no private channel. Revisit: the day the repo is made public.
- **GUI limits are fixed by the spec (§10).** Why: a vault that stays open, or leaks through the clipboard or screen, defeats the encryption, so the maxima are fixed, not user choices: auto-lock at most 60 min with no Never, clipboard clear at most 90 s, passwords re-hide after 30 s and phrases after 60 s, everything hides on blur and lock, weakening a setting needs the password, window title always "Holm". Risk: a user who wants longer limits cannot have them. Revisit: on owner request.
- **The only GUI font is the bundled Atkinson Hyperlegible (OFL-1.1); egui `default_fonts` is off.** Why: the default fonts bring OFL-1.1 and Ubuntu-font-1.0 files that `deny.toml` does not allow. Risk: the font's OFL-1.1 licence text must ship with the repo and binary (a `LICENSES/` or `NOTICE` note when the GUI lands); `deny.toml` checks crate licences only and does not see a bundled TTF. Non-Latin and emoji titles render as boxes. Revisit: if Latin-only coverage becomes a problem.

## Phase 2 (planned 2026-10-18)

- **Throttle lives in memory inside `Session`.** Why: spec §11; an on-disk record was tamperable in the old project. It survives lock and unlock, counts every unlock error as a failure (F16: wrong password, format, store, body, any error) with two exceptions decided on public bytes before any Argon2 run, so no password is tested: a missing file (`NoVault`) and KDF costs the header parser refuses (`KdfPolicy`); enforced through `Throttle::attempt` (it refuses without running the action, counts before running it, and resets only on success), covers unlock, phrase reveal, password change, settings weakening and CSV export, and runs on the monotonic clock so a wall-clock change cannot skip a delay. Risk: a restart resets it. Revisit: if an online oracle ever appears.
- **Generator uses OS randomness only, with rejection sampling.** Why: no userspace PRNG to seed wrongly, and no modulo bias; minimum digit and symbol counts are met by redrawing the whole password, so output is uniform over valid passwords. Limits: length 12-128, required counts at most half the length, estimated entropy at least 64 bits; passphrases 6-20 EFF words. Risk: a site that wants a short PIN needs a hand-typed password. Revisit: on owner request.
- **Imports are treated as hostile.** Why: the file comes from outside Holm. 16 MiB cap before parsing, strict UTF-8, at most 50 000 rows and 64 columns, unknown or duplicate columns reject the file, rows pass the same field rules as manual entry and are reported by number and reason only, no category auto-create (owner: unmatched go to Uncategorised), all-or-nothing apply, dropped Safari OTP secrets are counted, rows that duplicate an existing item or an earlier row (same type, title, username and URLs after canonicalisation; owner answer) are skipped and counted, and a recovery row takes its phrase only from the `recovery` column (never `password` or `notes`, unlike the old importer). Risk: csv and serde_json scratch copies are not wiped (the source file is plaintext on disk anyway). Revisit: if a parser with wiping buffers becomes available.
- **Plaintext CSV export is password-gated and never overwrites.** Why: spec §8.8. Throttled password re-entry, fixed warning text, Trash excluded, one wiping allocation, written only by exclusive create with mode 0600. Columns: the 11 import columns, then `favourite`, `created`, `updated` (owner answer), which import reads back. No formula escaping, because it would change passwords starting with `=`, `+`, `-` or `@` and break migration; the warning says not to open the file in a spreadsheet. Risk: a user opens it in a spreadsheet anyway. Revisit: if users report spreadsheet use.
- **Durable save: exclusive temp in the same directory, sync, rename, sync directory.** Why: spec §9; atomic rename and no backup-file juggling. Temps are named `<file>.tmp-<16 hex>` with mode 0600; the vault must be a regular file (no symlinks); `create_new` never overwrites (hard link, or exclusive create where links are unsupported) and removes its temp in every branch; unlock removes only exact-pattern temps. A directory sync that returns `Unsupported` (some FAT/exFAT volumes, such as a USB stick) counts as success, and any other directory-sync error fails the save; a macOS test on a real exFAT disk image (`hdiutil`) covers it. Crash tests stop a child at each step with `exit`. Risk: that models a killed process, not power loss; Windows write-through, directory sync and the file lock are not done yet. Revisit: Phase 4 per-OS checklist.
- **`holm-platform` is created in Phase 2, std only, still `forbid(unsafe_code)`.** Why: the crash tests must run against the real save path. Risk: none; Phase 4 relaxes the lint per module when OS code lands. Revisit: Phase 4.
- **Every item string wipes on drop; `Debug` never prints item text.** Why: usernames and URLs are personal too, and wiping is cheap. Display fields reject control and bidi characters so titles cannot be spoofed; single-line secrets reject NUL, CR and LF. A URL is optional, and when present is non-empty with no leading or trailing whitespace, so it survives export and import unchanged (import trims, then validates). Item passwords are never trimmed or normalised. Risk: some odd legacy titles are refused on import. Revisit: on user reports.
- **Size limits on vault content.** Why: bounded memory and file size. 50 000 items, 256 categories (names up to 64 characters), 1024 bytes per display field, 4096 per password or phrase, 65 536 per note, 32 URLs per login; a change that would pass 64 MiB is rolled back. Risk: a very large vault hits a limit. Revisit: if a user does.
- **The recovery phrase gate is enforced in core.** Why: spec §7; a UI bug must not be able to show a phrase. `GatedSecret` has no public accessor and `Session::reveal_phrase` checks the password through the throttle each time. Risk: none known. Revisit: never weaker.
- **Security settings have fixed ranges and are clamped toward strict on load.** Why: spec §8.9 and §10. Auto-lock 60-3600 s (default 300), clipboard 5-90 s (default 30), lock on sleep on by default; weakening, including a lower generator entropy, needs the password. An out-of-range value in an authenticated body is clamped, not rejected, so a vault never becomes unopenable over a setting. Risk: none known. Revisit: on owner request.
- **Body schema: `u16` version prefix, then postcard; newer schemas refused.** Why: an old Holm must never rewrite a newer vault and drop its fields. Trailing bytes rejected; data validated after decoding. Risk: users must upgrade Holm to open newer vaults. Revisit: on the first schema bump.
- **The master password strength check is Holm's own code; the `zxcvbn` crate is a test oracle only (COS ruling on #16, 2026-10-18).** Why: the crate added 17 unreviewed production crates to `holm-core`, read the clock, and left un-wiped copies of the master password in the heap. Holm ports its model (matchers and minimum-guesses split), embeds its MIT frequency lists with a pinned SHA-256, wipes every derived buffer and scores the whole password with bounded work. Accepted: 12 to 1,024 NFC characters and an estimate of at least 1e10 guesses (score 4; raised from score 3 in fix round 1, because score 3 accepts `Summer2026!!`). Longer input is refused unscored, so a paste cannot freeze the app. A dev-only oracle test on a fixed corpus and a fixed-seed generated corpus checks that every password zxcvbn scores below 4 is refused and that Holm never scores higher. Risk: an estimator bug accepts a weak password outside the corpus; the lists are English-centric. Revisit: when the lists or zxcvbn's model change, or on a false-accept report.
- **`blake2` is a direct dependency to turn on its `zeroize` feature.** Why: argon2's BLAKE2b state then wipes on drop (feature unification, same as `poly1305`). Risk: none. Revisit: if argon2 enables it itself.
- **cargo vet: imported audits first, `trust` only for well-known publishers, exemptions only for dev-only or unused-target crates; libc and syn must leave the exemption list.** Why: closes the 12-exemption deferral. Risk: a trusted publisher's account is compromised. Revisit: Phase 6.
- **`holm-core` gets a `fuzzing` feature for fixed-key seal and open.** Why: spec §12 full-open fuzzing needs a known key. Only `fuzz/` enables it. Risk: shipping it would expose key-handling helpers. Revisit: Phase 6, where the `--all-features` release guard covers it with `test-vectors`.
- **The Argon2 work area is reserved with `try_reserve_exact` (since Phase 1); from Phase 2 a refusal is reported as `OutOfMemory`.** Why: a refused allocation becomes an `OutOfMemory` error (the unlock screen's "not enough memory") instead of an abort. Risk: with memory overcommit the OS may still kill the process later. Revisit: Phase 4 with `mlock`.
- **An undo after an oversize change restores the earlier dirty flag.** Why: forcing the session clean would hide an earlier unsaved edit, and lock would not warn before discarding it. Risk: none known. Revisit: never weaker.
- **`change_password` uses `envelope::create`, then the write, then the key swap, not `envelope::rekey`.** Why: `rekey` swaps the keys before the caller writes, so a failed write would leave memory and disk on different passwords. Risk: `rekey` stays as an unused but tested API. Revisit: if `rekey` gains a two-phase form.
- **Built-in categories are ordinary categories after creation.** Why: owner answer 2026-10-18; Personal, Work and Community can be renamed and deleted like user ones. Risk: none. Revisit: on owner request.
- **Item and text types have no public serde.** Why: a public `Serialize` on `Item` or `GatedSecret` would let any code write a secret to bytes, and a public `Deserialize` would build an item that skipped the field rules. Serde sits on crate-private wire types that re-run every rule on decode, and `compile_fail` doctests check the public types stay non-serde. Risk: the body codec needs the wire types and a little mapping code. Revisit: if the codec moves to another crate, or if a second consumer needs the wire types.
- **serde, serde_core and serde_derive are trusted through dtolnay for safe-to-deploy.** Why: they are now normal dependencies of `holm-core`, and the same maintainer already covers `syn`. The 1.0.228 to 1.0.229 delta audits stay at safe-to-run. Risk: a compromised dtolnay account. Revisit: at the trust entries' end date (2027-10-17).
- **The golden vault is deterministic and holds the schema-1 default body (Task 7).** Why: the first golden predated the body format and used random salt, DEK and nonces, so it could not be rebuilt. `tests/golden_vault.rs` now builds it with fixed fills (salt `0x11`, DEK `0x22`, wrap nonce `0x33`, body nonce `0x44`), password `"caf\u{e9} golden"` at `KdfParams::FLOOR`, and checks the committed file matches byte for byte; the header layout is unchanged. It seals with `chacha20poly1305` directly (a dev-dependency already in the graph through holm-crypto), because holm-crypto's `Nonce` cannot be fixed on purpose. Risk: none; fixed key material exists only in this test vector. Revisit: on a format or schema version bump, by adding a new golden and keeping this one.

## Roadmap reorder (2026-10-18, owner-approved)

- **Phases are now 2a core, 3 macOS walking skeleton, 4 = 2b + CLI, 5 platform hardening + GUI polish, 6 release.** Why: a thin, runnable macOS app comes early and is hardened later. Spec §14 has the details. Revisit: at the end of Phase 3.
- **Phase 2a ships Tasks 7, 8, 10 and a reduced 13 (2 new fuzz targets, 5 in total; round trip without export or import).** Tasks 9 (search), 11 (import) and 12 (export) move to Phase 4 and keep their numbers. Task 10 adds `Session::active_items` because search moved.
- **Phase 3 ships a `holm-gui` egui app on `Session<FsStore>`** with these screens: create (strength meter), unlock (throttle wait), item list, login add/edit/view, copy, lock, idle and minimise lock. The vault lives at `~/Library/Application Support/Holm/holm.vault`. Done = `cargo run -p holm-gui --locked` can create, add, lock, unlock and see the item.
- **The security floor is unchanged:** no plaintext on disk, secrets in wiping types, no secret logging, every unlock through `Throttle`. Clipboard auto-clear, keychain, Touch ID, mlock, capture exclusion and signing move to Phase 5/6. Risk: in Phase 3 the clipboard is not cleared, so the copy button says so. Revisit: Phase 5.
- **GUI deps are `eframe =0.37.0` (`glow` and `accesskit` only; no clipboard, persistence or default fonts) and `arboard =3.7.0` (no default features, `exclude_from_history`), both macOS-only target deps.** Fonts are Atkinson Hyperlegible Next and Mono (OFL-1.1), hash-gated like the wordlist.
- **`deny.toml` gets `[graph] targets` (5 desktop triples, which keeps winit's wasm-only path to `tokio` out) and allows `ISC` and `BSL-1.0`.** The ban list does not change.
- **Vet policy for GUI crates (needs a COS yes): imports first, then `trust` only for publishers an imported set already trusts.** The rest get exemptions noted `gui-only, pre-release; audit or replace before Phase 6`. holm-core and holm-crypto stay exemption-free. Revisit: before Phase 6.
- **Review depth follows risk.** Opus reviews crypto, password, file-format and `unsafe` work; Sonnet reviews mechanical work. Only Critical/Important findings block, with one fix round per task. Nits go into a final fix wave. The next task's implementation overlaps the previous task's review. Lessons and issues never block.
- **Phase 6 paid and public steps (signing certificate, outside audit, going public) need owner approval.**
