# Decisions and accepted risks

One line per decision: what we chose, why, the risk we accept, and when to revisit.
The binding design is `docs/superpowers/specs/2026-10-17-holm-v1-design.md`; this file
records the choices made while building Phase 0-1 and planning Phase 2
(`docs/superpowers/plans/2026-10-18-phase-2-holm-core.md`).

- **Local CI replaces GitHub Actions until the repo is public.** Why: Actions is manual-only for now, and `scripts/ci-local.sh` already runs all 11 gates. Risk: a Linux- or Windows-only bug ships unnoticed. Revisit: before going public, re-enable Actions (3-OS CI, scheduled fuzzing, oracle and fuzz jobs, checksummed cargo-deny install) and GitHub private vulnerability reporting.
- **The test-only oracle uses unsafe FFI to libsodium.** Why: an independent Argon2id cross-check for the `argon2` crate, which has no outside audit. It sits in one `#[allow(unsafe_code)] mod ffi` with a `// SAFETY:` comment on every block, in a separate workspace that never ships. Risk: a bug in the test harness itself. Revisit: if the oracle ever joins the product graph (it must not).
- **The oracle ignores RUSTSEC-2026-0367, -0368 and -0369 (zip 8.6.0) in `cargo audit`.** Why: zip is a build dependency of `libsodium-sys-stable`, used by its build script only for Windows MSVC targets, on an archive checked first (the local gate skips the oracle on Windows), in a workspace that never ships. Risk: a build-time issue on a Windows dev machine. Revisit: remove the ignores once `libsodium-sys-stable` moves to zip 9.
- **Nothing is locked in RAM yet (no `mlock`).** Why: locking is platform work, and secrets are wiped on drop. Risk: the OS may swap secrets, including the Argon2 work area, to disk while in use (listed in `docs/CRYPTO.md` known gaps). Revisit: in the platform phase.
- **Timing difference between wrong password and damaged body is accepted, not hidden.** Why: Argon2 dominates the cost, and the difference only shows whether the key unwrap succeeded, which anyone holding the file can test offline at the same Argon2 cost. Risk: none beyond what the file already allows. Revisit: only if an online oracle ever appears. See `docs/CRYPTO.md`, Timing.
- **Nonce misuse resistance by type.** Why: `Nonce` has no `Clone`, `Copy` or `Default`, is made only by `Nonce::random()`, and `seal` takes it by value, so a nonce cannot be reused through the API. Risk: a small API rework later. Revisit: if a format needs deterministic nonces.
- **`rekey` takes `&mut VaultKeys` and replaces the keys only on success.** Why: a failed rekey leaves the old keys working (atomic from the caller's view). Risk: none known. Revisit: if keys become shared across threads.
- **Padding is canonical.** Why: each body has exactly one padded form (16 KiB blocks, u32 LE prefix), and `unpad` rejects any other, so there is no malleable padding. Risk: a future writer must follow the same rule. Revisit: on a format version bump.
- **Full-open fuzzing: closed in Phase 2 Task 13 (#25).** The `open_fixed_key` target runs the whole open (envelope, padding, body decode) with a fixed KEK through holm-core's test-only `fuzzing` feature, and `decode_body` fuzzes the bounded body decode with a 64 MiB per-allocation limit. Both run in the `ci-local` fuzz gate. Why a feature: skipping Argon2 is what makes the target fast, and that shortcut must not exist in a shipping build. Risk: the feature being turned on in a release. holm-core stops with a `compile_error!` when `fuzzing` is on without `--cfg fuzzing` (which only cargo-fuzz sets), and the `fuzzing-guard` gate proves a plain `cargo check --features fuzzing` fails. Revisit: when the body schema changes.
- **SBOM and the `--all-features` release guard are deferred to Phase 6.** Why: both are release work. The guard must fail a release build that turns on holm-crypto's `test-vectors` (the raw Argon2 KAT helper) or holm-core's `fuzzing` (seal and open with a raw KEK, no Argon2). Today only `oracle/` and `fuzz/` enable them. `fuzzing` already refuses to build without `--cfg fuzzing` (a `compile_error!`, proven by the `fuzzing-guard` gate), and `scripts/ci-local.sh` lints it in its own clippy gate under that cfg. Risk: none for unreleased code. Revisit: Phase 6.
- **3 `cargo vet` exemptions remain, all dev-only or unused-target.** Why: Phase 2 Task 1 (#13) moved libc and syn 2 and 3 to `cargo vet trust` (syn: dtolnay; libc: its crates.io trusted publisher `github:rust-lang/libc`, because releases since 0.2.190 no longer come from rust-lang-owner), and the dev-only rustix and linux-raw-sys (sunfishcode), windows-sys (kennykerr) and toml_edit, toml_parser and winnow (epage) to safe-to-run trust of publishers that isrg, mozilla and ariel-os already trust; r-efi (unused UEFI target), borsh-derive and proptest (dev-only, no trusted publisher) stay exempt with their reasons in `supply-chain/config.toml`. Risk: a trusted publisher's account, or libc's release workflow, is compromised. Revisit: before the trust entries end on 2027-10-17, and at Phase 6.
- **The cargo-deny-action is pinned to a full commit SHA (v2.1.1).** Why: a moving tag is a supply-chain hole. Risk: the action downloads its binary without a checksum. Revisit: when Actions is re-enabled, move to a checksummed install and keep it on the same cargo-deny version as `scripts/ci-local.sh`.
- **Re-enable Actions and private vulnerability reporting before going public.** Why: SECURITY.md tells reporters to use GitHub private reporting, and the spec wants 3-OS CI. Risk: if forgotten, reports have no private channel. Revisit: the day the repo is made public.
- **GUI limits are fixed by the spec (§10).** Why: a vault that stays open, or leaks through the clipboard or screen, defeats the encryption, so the maxima are fixed, not user choices: auto-lock at most 60 min with no Never, clipboard clear at most 90 s, passwords re-hide after 30 s and phrases after 60 s, everything hides on blur and lock, weakening a setting needs the password, window title always "Holm". Risk: a user who wants longer limits cannot have them. Revisit: on owner request.
- **The only GUI font is the bundled Atkinson Hyperlegible (OFL-1.1); egui `default_fonts` is off.** Why: the default fonts bring OFL-1.1 and Ubuntu-font-1.0 files that `deny.toml` does not allow. Risk: the font's OFL-1.1 licence text must ship with the repo and binary (a `LICENSES/` or `NOTICE` note when the GUI lands); `deny.toml` checks crate licences only and does not see a bundled TTF. Non-Latin and emoji titles render as boxes. Revisit: if Latin-only coverage becomes a problem.

## Phase 2 (planned 2026-10-18)

- **Throttle lives in memory inside `Session`.** Why: spec §11; an on-disk record was tamperable in the old project. It survives lock and unlock, counts every unlock error as a failure (F16: wrong password, format, store, body, any error) with two exceptions decided on public bytes before any Argon2 run, so no password is tested: a missing file (`NoVault`) and KDF costs the header parser refuses (`KdfPolicy`); enforced through `Throttle::attempt` (it refuses without running the action, counts before running it, and resets only on success), covers unlock, phrase reveal, password change, settings weakening and CSV export, and runs on the monotonic clock so a wall-clock change cannot skip a delay. Risk: a restart resets it. Revisit: if an online oracle ever appears.
- **Generator uses OS randomness only, with rejection sampling.** Why: no userspace PRNG to seed wrongly, and no modulo bias; minimum digit and symbol counts are met by redrawing the whole password, so output is uniform over valid passwords. Limits: length 12-128, required counts at most half the length, estimated entropy at least 64 bits; passphrases 6-20 EFF words. Risk: a site that wants a short PIN needs a hand-typed password. Revisit: on owner request.
- **Imports are treated as hostile.** Why: the file comes from outside Holm. 16 MiB cap before parsing, strict UTF-8, at most 50 000 rows and 64 columns, unknown or duplicate columns reject the file, rows pass the same field rules as manual entry and are reported by number and reason only, no category auto-create (owner: unmatched go to Uncategorised), all-or-nothing apply, dropped Safari OTP secrets are counted, rows that duplicate an existing item or an earlier row (same type, title, username and URLs after canonicalisation; owner answer) are skipped and counted, and a recovery row takes its phrase only from the `recovery` column (never `password` or `notes`, unlike the old importer). Risk: the source file is plaintext on disk; the old risk that csv and serde_json scratch copies are not wiped is closed (Phase 4 Task 2, "Own CSV and JSON code" below): every parsed cell is a wiping buffer, so the caller's file buffer is the only remaining copy, and Phase 4 Task 4 (`read_capped`) makes that one wiping too. Revisit: if the import formats grow beyond flat CSV and flat JSON objects.
- **Plaintext CSV export is password-gated and never overwrites.** Why: spec §8.8. Throttled password re-entry, fixed warning text, Trash excluded, one wiping allocation, written only by exclusive create with mode 0600. Columns: the 11 import columns, then `favourite`, `created`, `updated` (owner answer), which import reads back. No formula escaping, because it would change passwords starting with `=`, `+`, `-` or `@` and break migration; the warning says not to open the file in a spreadsheet. Risk: a user opens it in a spreadsheet anyway. Revisit: if users report spreadsheet use.
- **Durable save: exclusive temp in the same directory, sync, rename, sync directory.** Why: spec §9; atomic rename and no backup-file juggling. Temps are named `<file>.tmp-<16 hex>` with mode 0600; the vault must be a regular file (no symlinks); `create_new` never overwrites (hard link, or exclusive create where links are unsupported) and removes its temp in every branch; unlock removes only exact-pattern temps. A directory sync that fails with `ErrorKind::Unsupported` or raw `ENOTSUP` or `EINVAL` (some FAT/exFAT and network volumes, such as a USB stick; F30 amended after Task 10, because std on macOS leaves `ENOTSUP` uncategorised) counts as success, and any other directory-sync error fails the save; a file sync is never relaxed this way. A macOS test on a real exFAT disk image (`hdiutil`) covers it. A `replace` error after the rename (a failed directory sync) may leave the new bytes in full, so the session treats any `replace` error as old-or-new and stays dirty. Crash tests stop a child at each step with `exit`. Risk: that models a killed process, not power loss; Windows write-through, directory sync and the file lock are not done yet. Known gap: where hard links are unsupported (FAT, exFAT), the `create_new` fallback is not crash-atomic, so a crash while creating a vault there can leave a short file that blocks a new `create`; fix in Phase 5. Revisit: Phase 5 per-OS checklist.
- **`holm-platform` is created in Phase 2, std only, `forbid(unsafe_code)` per module.** Why: the crash tests must run against the real save path. Phase 3 adds one `unsafe` block, in `window` under the macOS-only `gui-window` feature (reads NSWindow `isMiniaturized`); every other module forbids `unsafe_code`, so a `--workspace` build that turns the feature on cannot widen it. Risk: one reviewed unsafe surface. Revisit: Phase 5.
- **Every item string wipes on drop; `Debug` never prints item text.** Why: usernames and URLs are personal too, and wiping is cheap. Display fields reject control and bidi characters so titles cannot be spoofed; single-line secrets reject NUL, CR and LF. A URL is optional, and when present is non-empty with no leading or trailing whitespace, so it survives export and import unchanged (import trims, then validates). Item passwords are never trimmed or normalised. Risk: some odd legacy titles are refused on import. Revisit: on user reports.
- **Size limits on vault content.** Why: bounded memory and file size. 50 000 items, 256 categories (names up to 64 characters), 1024 bytes per display field, 4096 per password or phrase, 65 536 per note, 32 URLs per login; a change that would pass 64 MiB is rolled back. Risk: a very large vault hits a limit. Revisit: if a user does.
- **The recovery phrase gate is enforced in core.** Why: spec §7; a UI bug must not be able to show a phrase. `GatedSecret` has no public accessor and `Session::reveal_phrase` checks the password through the throttle each time. Risk: none known. Revisit: never weaker.
- **Security settings have fixed ranges and are clamped toward strict on load.** Why: spec §8.9 and §10. Auto-lock 60-3600 s (default 300), clipboard 5-90 s (default 30), lock on sleep on by default; weakening, including a lower generator entropy, needs the password. An out-of-range value in an authenticated body is clamped, not rejected, so a vault never becomes unopenable over a setting. Risk: none known. Revisit: on owner request.
- **Body schema: `u16` version prefix, then postcard; newer schemas refused.** Why: an old Holm must never rewrite a newer vault and drop its fields. Trailing bytes rejected; data validated after decoding. Risk: users must upgrade Holm to open newer vaults. Revisit: on the first schema bump.
- **The master password strength check is Holm's own code; the `zxcvbn` crate is a test oracle only (COS ruling on #16, 2026-10-18).** Why: the crate added 17 unreviewed production crates to `holm-core`, read the clock, and left un-wiped copies of the master password in the heap. Holm ports its model (matchers and minimum-guesses split), embeds its MIT frequency lists with a pinned SHA-256, wipes every derived buffer and scores the whole password with bounded work. Accepted: 12 to 1,024 NFC characters and an estimate of at least 1e10 guesses (score 4; raised from score 3 in fix round 1, because score 3 accepts `Summer2026!!`). Longer input is refused unscored, so a paste cannot freeze the app. A dev-only oracle test on a fixed corpus and a fixed-seed generated corpus checks that every password zxcvbn scores below 4 is refused and that Holm never scores higher. Risk: an estimator bug accepts a weak password outside the corpus; the lists are English-centric. Revisit: when the lists or zxcvbn's model change, or on a false-accept report.
- **`blake2` is a direct dependency to turn on its `zeroize` feature.** Why: argon2's BLAKE2b state then wipes on drop (feature unification, same as `poly1305`). Risk: none. Revisit: if argon2 enables it itself.
- **cargo vet: imported audits first, `trust` only for well-known publishers, exemptions only for dev-only or unused-target crates; libc and syn must leave the exemption list.** Why: closes the 12-exemption deferral. Risk: a trusted publisher's account is compromised. Revisit: Phase 6.
- **`holm-core` gets a `fuzzing` feature for fixed-key seal and open.** Why: spec §12 full-open fuzzing needs a known key. Only `fuzz/` enables it. Risk: shipping it would expose key-handling helpers. A `compile_error!` stops any build that turns it on without `--cfg fuzzing`, so even `--all-features` cannot ship it. Revisit: Phase 6, where the `--all-features` release guard also covers `test-vectors`.
- **The Argon2 work area is reserved with `try_reserve_exact` (since Phase 1); from Phase 2 a refusal is reported as `OutOfMemory`.** Why: a refused allocation becomes an `OutOfMemory` error (the unlock screen's "not enough memory") instead of an abort. Risk: with memory overcommit the OS may still kill the process later. Revisit: Phase 5 with `mlock`.
- **An undo after an oversize change restores the earlier dirty flag.** Why: forcing the session clean would hide an earlier unsaved edit, and lock would not warn before discarding it. Risk: none known. Revisit: never weaker.
- **`change_password` uses `envelope::create`, then the write, then the key swap, not `envelope::rekey`.** Why: `rekey` swaps the keys before the caller writes, so a failed write would leave memory and disk on different passwords. Risk: `rekey` stays as an unused but tested API. Revisit: if `rekey` gains a two-phase form.
- **Built-in categories are ordinary categories after creation.** Why: owner answer 2026-10-18; Personal, Work and Community can be renamed and deleted like user ones. Risk: none. Revisit: on owner request.
- **Item and text types have no public serde.** Why: a public `Serialize` on `Item` or `GatedSecret` would let any code write a secret to bytes, and a public `Deserialize` would build an item that skipped the field rules. Serde sits on crate-private wire types that re-run every rule on decode, and `compile_fail` doctests check the public types stay non-serde. Risk: the body codec needs the wire types and a little mapping code. Revisit: if the codec moves to another crate, or if a second consumer needs the wire types.
- **serde, serde_core and serde_derive are trusted through dtolnay for safe-to-deploy.** Why: they are now normal dependencies of `holm-core`, and the same maintainer already covers `syn`. The 1.0.228 to 1.0.229 delta audits stay at safe-to-run. Risk: a compromised dtolnay account. Revisit: at the trust entries' end date (2027-10-17).
- **The golden vault is deterministic and holds the schema-1 default body (Task 7).** Why: the first golden predated the body format and used random salt, DEK and nonces, so it could not be rebuilt. `tests/golden_vault.rs` now builds it with fixed fills (salt `0x11`, DEK `0x22`, wrap nonce `0x33`, body nonce `0x44`), password `"caf\u{e9} golden"` at `KdfParams::FLOOR`, and checks the committed file matches byte for byte; the header layout is unchanged. It seals with `chacha20poly1305` directly (a dev-dependency already in the graph through holm-crypto), because holm-crypto's `Nonce` cannot be fixed on purpose. Risk: none; fixed key material exists only in this test vector. Revisit: on a format or schema version bump, by adding a new golden and keeping this one.

## Roadmap reorder (2026-10-18, owner-approved)

- **Phases are now 2a core, 3 macOS walking skeleton, 4 = 2b + CLI, 5 platform hardening + GUI polish, 6 release.** Why: a thin, runnable macOS app comes early and is hardened later. Spec §14 has the details. Revisit: at the end of Phase 3.
- **Phase 2a ships Tasks 7, 8, 10 and a reduced 13 (2 new fuzz targets, 5 in total; round trip without export or import).** Tasks 9 (search), 11 (import) and 12 (export) move to Phase 4 and keep their numbers. Task 10 adds `Session::active_items` because search moved.
- **Phase 3 ships a `holm-gui` egui app on `Session<FsStore>`** with these screens: create (strength meter), unlock (throttle wait), item list, login add/edit/view, copy, lock, idle and minimise lock. The vault lives at `~/Library/Application Support/Holm/holm.vault`. Done = `cargo run -p holm-gui --locked` can create, add, lock, unlock and see the item.
- **The security floor is unchanged:** no plaintext on disk, secrets in wiping types, no secret logging, every unlock through `Throttle`. Clipboard auto-clear, keychain, Touch ID, mlock, capture exclusion and signing move to Phase 5/6. Risk: in Phase 3 the clipboard is not cleared, so the copy button says so. Revisit: Phase 5.
- **GUI deps are `eframe =0.37.0` (`glow` and `accesskit` only; no clipboard, persistence or default fonts) and `arboard =3.7.0` (no default features, `exclude_from_history`), both macOS-only target deps.** Fonts are Atkinson Hyperlegible Next and Mono (OFL-1.1), hash-gated like the wordlist.
- **`deny.toml` gets `[graph] targets` (5 desktop triples, which keeps winit's wasm-only path to `tokio` out), allows `BSL-1.0`, and allows `ISC` for `libloading` only.** The ban list does not change. `BSL-1.0` comes only from `clipboard-win` and `error-code` (arboard's Windows back end), which no Holm target builds. `ISC` is a crate-scoped exception, not a global allow, because `libloading` is built on macOS: eframe always turns on glutin's `egl` feature. Three unmaintained-crate advisories (RUSTSEC-2026-0370 `zvariant`, -0371 `zbus_names`, -0372 `zvariant_derive`) are ignored with reasons: they sit on accesskit's Linux-only path, which Holm does not build. Revisit: Phase 5, or when zbus 6 lands.
- **Vet policy for GUI crates (COS ruling): imports first, then `trust` only for publishers an imported set already trusts.** The rest get exemptions noted `gui-only, pre-release; audit or replace before Phase 6`. holm-core, holm-crypto and holm-platform get no new exemption for a normal (non-dev) dependency; holm-core's dependency tree is unchanged. Phase 3 Task 1 result: 260 new locked crate versions; 39 are covered by imported audits or existing trusts, 49 new `trusted` entries (53 versions, publishers trusted by an imported set with a current end date) all end 2026-12-31, and 206 exemptions (188 new versions, plus 18 already-locked crates the GUI now needs at `safe-to-deploy`). Nothing is self-certified. Revisit: before Phase 6.
- **`envelope::open` and `verify_password` are `pub(crate)`; every password check outside holm-core goes through `Session`.** Why: a public check that skips the throttle lets a caller guess passwords at full speed. GUI and CLI use only the public `Session` methods (`Session::unlock`, and `change_password` and the other methods that take a password); these count failures and delay. `check_password` is `pub(crate)`. Risk: tests outside the crate cannot open an envelope directly; they use `Session` with a byte store, or in-crate tests. Revisit: if a tool needs an offline check, add a narrow throttled entry point, never re-export these.
- **Review depth follows risk.** Opus reviews crypto, password, file-format and `unsafe` work; Sonnet reviews mechanical work. Only Critical/Important findings block, with one fix round per task. Nits go into a final fix wave. The next task's implementation overlaps the previous task's review. Lessons and issues never block.
- **Phase 6 paid and public steps (signing certificate, outside audit, going public) need owner approval.**
- **Single-instance lock: `File::try_lock` on `<vault dir>/holm.lock`, held for the app lifetime, in holm-platform (Phase 3).** Why: two windows on one vault could overwrite each other's saves and lose data. A second instance shows fixed text and does not open the vault. Risk: a lock file stays on disk (empty, holds no secret); some network filesystems ignore advisory locks. Revisit: Phase 5 (the last-used vault path stays deferred).
- **OFL-1.1 is not added to `deny.toml`.** Why: bundled fonts are files, not crates, so cargo-deny never sees them. The licence is in `LICENSES/OFL-1.1.txt` and `NOTICE`, and `scripts/ci-local.sh` checks both font files' SHA-256. Revisit: if a font ships as a crate.

## Phase 3 (macOS walking skeleton, 2026-10-18)

The plan's Security decisions (`docs/superpowers/plans/2026-10-18-phase-3-macos-skeleton.md`). The GUI dependencies, the vet policy for GUI crates, the single-instance lock and the OFL-1.1 note are the lines above in "Roadmap reorder". Known gaps are in `docs/CRYPTO.md`, "The macOS app (Phase 3)".

- **Copy uses arboard with `exclude_from_history()` (`org.nspasteboard.ConcealedType`), never egui's `copy_text`, and there is no auto-clear in Phase 3.** Why: Holm owns the one path a secret takes to the clipboard, and eframe's `clipboard` feature would add image decoders. `clipboard_shortcuts` is off, so Cmd+C and Cmd+X copy nothing from Holm's window. Cmd+V goes straight from arboard into the wiping buffer for a `SecretField`, and becomes an `Event::Paste` for a plain field. Risk: a copied password stays on the clipboard, readable by any app and sent over Universal Clipboard, until replaced; the Copy button says so. Revisit: Phase 5 (auto-clear, clear on lock).
- **A revealed password is drawn with a non-selectable egui label.** Why: egui has no wiping text path. Risk: the text sits in egui's galley cache and in the label's AccessKit node while shown (F11), and is not wiped. Reveal hides after `REHIDE_PASSWORD_SECS`, on focus loss and on lock, and while hidden no AccessKit node holds it (tested). Revisit: Phase 5 GUI polish, if egui gains a way to drop a galley at once.
- **Title, username and URL use `TextEdit` over a capped, pre-allocated `Zeroizing<String>`.** Why: they are display text, not secrets (spec §8), and need normal editing. Risk: `TextEdit`'s undo history keeps plain `String` copies. Revisit: if any of these fields ever holds a secret.
- **Lock is `Session::lock` plus replacing the vault screen, so `Drop` wipes every form buffer.** Manual lock (button, Cmd+L) asks first when changes are unsaved ("Save and lock", "Lock anyway", "Cancel"); a failed save keeps the vault open. Idle and minimise locks never wait: they lock at once and say that unsaved changes were discarded. The idle check runs in `tick` (eframe `logic`), so it fires while no frame is drawn. Why: an unattended vault must lock even if nobody can answer a dialog. Risk: an idle or minimise lock can drop an unsaved change after a failed save. Revisit: Phase 5 (OS sleep, screen lock and logout events).
- **The Phase 3 GUI stays on the default path or `--vault`; the spec §8.0 last-used vault path is deferred.** Why: remembering a path needs a UI config file, which Phase 3 does not have (`persistence` is off). Risk: a vault elsewhere must be opened with `--vault`. Revisit: Phase 5.

## Phase 4 (search, import, export and holm-cli, 2026-10-18)

The plan's Security decisions (`docs/superpowers/plans/2026-10-18-phase-4-search-import-export-cli.md`), added by the task that implements each.

- **Own CSV and JSON code (Task 2).** Holm parses and writes CSV, and its narrow JSON import shape (one array of flat objects with string or `null` values), with std-only code in `holm_core::plain` instead of the `csv` crate (not in `Cargo.lock`) and `serde_json` at runtime. Why: neither crate can decode into a wiping buffer, and both keep scratch copies. Every cell is decoded into a `Zeroizing<String>` sized once from its raw span (CSV: the exact length; JSON: the raw length, an upper bound because escapes only shrink) and filled without growing, so no reallocation leaves a copy; the writer measures with `quoted_len` so the caller can allocate the whole file once. Both readers work on byte offsets, never recurse (JSON nesting is refused, not followed), cap cells, rows and keys, and fail with a line number only, never with input text. This adds no crate to `holm-core`; `serde_json` stays dev-only as a differential test oracle. Risk: about 550 lines (comments included) of hand-written parser. Covered by unit and property tests (round trip, agreement with serde_json, never-panics), fuzz targets in Task 3 and an Opus review. Revisit: if the import formats grow (nested JSON, other encodings).
- **Formula injection (Task 4): no escaping, unchanged.** Prefixing `'` or a tab to cells starting with `=`, `+`, `-` or `@` would change real passwords and break re-import into Holm or another manager (spec §8.8: no lock-in). Instead every cell is quoted, the fixed `EXPORT_WARNING` says the file is plain text and not to open it in a spreadsheet app, and the CLI (Task 6) and GUI (Task 8) require the master password plus an explicit confirmation after showing it. Pinned by `export_does_not_escape_formulas` (passwords `=SUM(A1)`, `+1`, `-1` and `@x` appear verbatim in the file and come back byte-exact through `parse` and `import`), `export_warning_names_spreadsheets`, `export_quotes_everything` and `export_needs_password_and_is_throttled`. Risk: a user opens the file in a spreadsheet anyway. Revisit: if users report spreadsheet use.
- **Reading an import file (Task 4).** `holm_platform::private_file::read_capped` checks the size with `fs::metadata` before opening, so an oversize file costs no memory; opens non-blocking on Unix (the `O_NONBLOCK` value from `fs_store`), so a FIFO swapped in cannot hang it; refuses anything but a regular file after following symlinks (a symlink to a regular file is the user's choice and is read); checks type and size again on the open handle; reads into one wiping buffer of the exact size; and refuses a file that grows (one more byte after the read) or shrinks (short read) while it is read. Errors carry a `StoreError` kind only, never a path. The export side, `write_new_private_file`, creates with `create_new` (never an existing file, a folder or any symlink, dangling or not) and mode 0600, syncs, and removes the file if the write or sync fails. Risk: between the failed write and the removal another process could swap the path, so the removal is best effort. Revisit: Phase 5 per-OS checklist (Windows ACLs for the 0600 rule).
- **Terminal input (Task 5).** `holm-cli` reads passwords only from `/dev/tty`, through `holm_platform::tty` (feature `tty`, rustix termios, safe API only, `forbid(unsafe_code)`): never from argv, an environment variable, stdin or a pipe, and with no controlling terminal it stops with fixed text. Any flag that looks like a password flag (`-p…`, `--pass…`, `--master…`, `--pw`, `--pwd`, with or without `=value`) is a usage error that names no value. Raw mode clears `ECHO`, `ECHONL`, `ICANON`, `ISIG` and `IEXTEN`; Holm's own line editor (`tty::edit`) handles Backspace, Ctrl-U, Ctrl-C and Ctrl-D, writes nothing when echo is off, and fills one pre-sized wiping buffer that never grows (past the cap it wipes and refuses). An RAII guard restores the saved mode on return, error and panic, flushing pending input first after a refusal or Ctrl-C. Because `ISIG` is off, Ctrl-C arrives as a byte and takes the same path. `VMIN = 1, VTIME = 0` without a deadline (a closed terminal reads as EOF, no busy loop) and `VMIN = 0, VTIME = 1` with one. Risk: a signal from outside (`kill`, SIGTERM, SIGHUP) ends the process without running the guard, which leaves echo off until `stty sane`; catching it would need `unsafe` or a new crate. Revisit: Phase 5, if a signal crate passes vet.
- **Typeahead is discarded (Task 6).** Raw mode starts with `tcsetattr(TCSAFLUSH)` (`OptionalActions::Flush`), not `TCSANOW`. Keys typed before a prompt appears were echoed in the clear (the terminal was still in normal mode) and, with `TCSANOW`, stayed queued and became the start of the password. `Flush` drops that queued input, so a secret is only what was typed after the no-echo prompt, and an early keypress can't end `wait_for_key` (the clipboard wait) at once. The echo itself can't be undone; it shows only what was typed too early. No headless test (it needs a pseudo-terminal); `manual_typeahead_is_discarded` is the manual check.
- **Per-process throttle (Task 5).** The CLI is one-shot: each command opens, asks up to three times, and locks on exit; there is no agent. The `Session` throttle lives in memory, so it starts fresh in every process, and three tries never reach its first wait (`FREE_FAILURES = 3`). A script that runs `holm` in a loop is limited only by Argon2 (about one guess per KDF run) and by the instance lock (one process at a time per vault folder). That is the same bound as an attacker with a copy of the file, so nothing is lost against the file-theft threat, and the strength check plus the Argon2 cost stay the real defence. Revisit: if a long-lived agent or shell (Task 7) keeps one `Session` across commands, its throttle carries over within that process.
- **Single instance in the CLI (Task 5).** Every command that touches a vault, `init` included, runs `ensure_vault_dir` and takes `holm.lock` before any prompt. A second Holm (GUI or CLI) gets fixed text and exit 1 without being asked for a password. `Opened` holds the session and the lock; its `Drop` locks the session before the lock is released. `gen` opens no vault and takes no lock.
- **Vet note scope (Task 5).** rustix 1.1.5 and its tree (linux-raw-sys, errno, libc, bitflags) were already in `Cargo.lock` and trusted safe-to-deploy for `holm-gui`. `holm-cli` now uses them through `holm-platform`'s `tty` feature, so the rustix and linux-raw-sys trust notes say "desktop clients" and the bitflags exemption says "desktop-only". Notes only: no new crate, no new trust entry, no criteria change. The Phase 6 audit-or-replace deadline still applies.
- **CLI copy (Task 6).** `holm get REF --copy FIELD` and `holm gen --copy` put one value on the macOS pasteboard through `holm_platform::clipboard` (feature `clipboard`, arboard's safe API, `exclude_from_history()` so clipboard managers are asked to skip it), then wait in the foreground until the vault's `clipboard_clear_secs` (30 s default; `gen` always uses 30 s) or until Enter. The vault is locked and its folder lock released before the wait, so the GUI can open meanwhile. When the wait ends Holm clears the clipboard only if it still holds Holm's value (read back into a wiping buffer and compared); if another app copied something since, Holm leaves it alone and says so. The clear runs even when the wait fails. A recovery phrase is copied only after the master password is typed again (`reveal_phrase`, throttled). A copied value is never printed. Off macOS `--copy` stops with fixed text and exit 1 before any prompt. Risk: if the process is killed during the wait, the value stays on the clipboard (and Universal Clipboard may already have sent it to other devices); the pasteboard keeps its own copy, which Holm cannot wipe. Revisit: Phase 5, with the GUI's auto-clear.
- **arboard's scope widened (Task 6).** arboard 3.7.0 was a `holm-gui`-only macOS dependency. It is now an optional macOS dependency of `holm-platform` behind the `clipboard` feature, which `holm-cli` turns on. No new crate and no `Cargo.lock` package change (only holm-platform's dependency list); the arboard and objc2-app-kit 0.3.2 exemption notes now say "desktop clients (holm-gui, holm-cli --copy)". Notes only: no new trust entry and no criteria change. The Phase 6 audit-or-replace deadline still applies.
- **CLI writes (Task 6).** Secrets for `add` and `edit` come only from hidden prompts; flags carry public fields only, and a flag that doesn't fit the item type is refused before any prompt (`add`, as a usage error) or before any secret prompt (`edit`, as a type-change error). `edit` copies every unchanged secret into the new input (`SecretText::new(x.expose().to_owned())`) and sends an empty phrase, which the core reads as "keep", so the CLI never reads a stored phrase to edit an item. `rm --forever` needs the item in the Trash and `delete` typed at a visible prompt. `passwd` asks for the current password, then the new one twice (a weak one is refused before the repeat); the core checks the current one through the throttle as part of `change_password`, so a wrong current password is reported after the new one is typed. If the change is uncertain, `passwd` saves once more under the new keys before it reports. Import reads and parses the file before the vault is opened, reports skipped rows by number and fixed reason only, and asks for `import` typed at a visible prompt; a save error other than "too large" says the items may not be saved and to keep the file. Export refuses any existing path before a prompt, then shows the warning, asks for `export`, and asks for the master password again, in that order.
